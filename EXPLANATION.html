PSE-A2-002: Incomplete import

Complyance · Product Support Engineer · Assignment 2 · How I owned the case from report to resolution

1. The case in short

Cedar Demo Malaysia said 12 records were accepted and the import says complete, but only seven results are visible, and asked whether to re-upload. I treated that as a report, not a diagnosis. The steps I took:

  1. Captured the real state.
  2. Reproduced it in an isolated database.
  3. Traced it to the exact code.
  4. Made a narrow fix with regression tests that fail before and pass after.
  5. Reconciled the existing import in place with the approved command.
  6. Wrote every customer update and the escalation without claiming anything I had not verified.

2. Principles I followed

  • Facts before conclusions. Records, results and events together, never just the counters or the word "completed".
  • Don't make it worse. No re-upload (no deduplication means duplicates), no reset of the original case, and reproduction only in a separate database.
  • Fix the cause, not the symptom. No bigger batch size, no edited fixtures, no faked counters.
  • Honest status. Local verification is not production restoration; release and customer confirmation stay "awaiting".
  • Support keeps ownership. Every message promises the next update; the engineering owner is "requested", not assumed.

4. Root cause (confirmed in code)

The worker paged through rows with an offset, but the query only returns rows that are still pending, and each batch removes its rows from that set:

// worker.ts (before)
let offset = 0;
while (true) {
  const batch = repository.pendingBatch(workspaceId, importId, batchSize, offset);
  if (batch.length === 0) break;
  repository.commitBatch(workspaceId, importId, batch);
  offset += batch.length;            // grows while the pending set shrinks
}
repository.finishImport(workspaceId, importId);   // marks "completed" with no check

-- repository.ts pendingBatch (before)
... WHERE state = 'pending' ORDER BY id LIMIT ? OFFSET ?
LoopPending setOffsetReturned
1DOC-001 to 0120DOC-001 to 005
2DOC-006 to 012 (7 rows)5DOC-011, 012 (006 to 010 skipped)
3DOC-006 to 010 (5 rows)7nothing, so it stops and marks completed

Any import with more rows than the batch size is affected. The starter tests used only 1 and 5 rows, so they never caught it.

5. The fix

// worker.ts (after): always take the FIRST pending rows
while (true) {
  const batch = repository.pendingBatch(workspaceId, importId, batchSize);
  if (batch.length === 0) break;
  repository.commitBatch(workspaceId, importId, batch);
}

-- repository.ts pendingBatch (after)
... WHERE state = 'pending' ORDER BY id LIMIT ?

// repository.ts finishImport (after): completion must be genuine
if (job.pending !== 0 || job.processed !== job.total) throw new Error(...);  // marks the import failed instead

The public API, CSV validation, batch limit, normalization and workspace scoping are unchanged.

6. Tests

tests/regression-batching.test.ts runs the real Bun server through the existing harness, with a fresh temporary database per lab. It covers:

  • the seeded customer case and the supplied 12-row fixture;
  • batch size 5 with 1, 4, 5, 6, 10, 11, 12, 13 and 200 rows;
  • batch size 3 with 2, 3, 4, 7 and 12 rows;
  • batch size 20 with 12, 20, 21, 41 and 200 rows;
  • batch size 1 with 1, 3 and 12 rows.

Each test asserts exact document refs, normalized labels, one result per record, the exact batch sizes, every record in exactly one batch, completion only with nothing pending, cross-workspace 404, and an unchanged paused control. Before the fix, exactly the volumes larger than the batch size failed; after it, all tests pass. The actual numbers are in the README and evidence/.

7. Recovering the existing case

  1. Restarted the original lab on the patched code (a completed case is never auto-requeued).
  2. Took a snapshot before recovery.
  3. Ran the approved bun run resume-case.
  4. The worker processed only DOC-006 to 010, in one batch of 5.
  5. Took a snapshot after recovery.
  6. Ran 13 automated checks: same import and record IDs, 12 results, 0 pending, the 7 earlier results unchanged, no duplicate processing, control unchanged.

9. Escalation

I escalated to engineering at P2, using a Linear-ready draft in the case report, for four reasons:

  • the patch needs independent review and release;
  • the lab shows every import larger than the batch size is affected, so other customers may have falsely "completed" imports, which needs a production query;
  • production reconciliation needs authorization;
  • notifying other customers needs a decision.

Support keeps the customer relationship and the next update time.
